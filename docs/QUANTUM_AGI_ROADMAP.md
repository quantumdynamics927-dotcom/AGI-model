# Quantum AGI Research Roadmap

> **Scope:** a 12-month, four-phase research path that turns the current
> "hardware-calibrated promoter validation" snapshot (see `README.md`)
> into a small but defensible piece of evidence that quantum hardware
> can carry an inference workload calibrated well enough to be useful.

This document is the canonical answer to the question the README ends
with: *"What comes after the 5-job calibration batch?"* It is also the
input to milestone 0, which is shipped as `backend_aware_offset.py`.

## Where we are today (May–June 2026)

The current state, honestly stated:

- **Calibration layer v2.0** lives in `quantum_calibration_framework.py`.
  It fits a single systematic offset (`-0.1381`) against an
  `ibm_fez` batch of 5 jobs. Pass rate post-calibration: 100 %.
- **The headline claim that should not be overclaimed:** a 100 % pass
  rate on 5 jobs is a calibration sanity check, not a theory result.
  The README already says this; the roadmap below is the path to
  earning the larger claim.
- **The next scientific question** is whether the offset is
  backend-specific and whether it transfers. The README's "Replicate-
  aware next phase" section lists four sub-questions:
  1. Within-promoter mean and variance,
  2. Between-promoter effect size,
  3. Calibration residual distribution,
  4. Backend-specific offset transferability.
  Phase P0 (below) addresses (4); P1 addresses (1)–(3).

The architecture of TMT-OS, the 13-node Hugging Face Space, and the
governance / vcapture layer are *not* on the critical path of this
roadmap. They are useful platforms for the experiments but the
scientific deliverables are the calibration results and the downstream
benchmark.

## How phases connect

```
P0 (offset) ──► P1 (replicates) ──► P2 (variational agent) ──► P3 (logical qubit)
   │                  │                     │                       │
   ▼                  ▼                     ▼                       ▼
backend-aware     within / between       first non-toy task     portability test
offsets, single   promoter stats,        under calibrated       on the cleanest
shrinkage         residual distribution   noise model            hardware available
```

Each phase produces a paper-style artifact (Markdown report + JSON
data) and a small test suite that gates the next phase.

## P0 — Backend-aware offset transferability (Milestone 0)

**Window:** Month 1–2 (target end of Month 2).

**Deliverable:**

- `backend_aware_offset.py` (shipped with this roadmap) — per-backend
  offset with James-Stein-style shrinkage toward the global mean when
  the per-backend sample count is small. Default shrinkage prior
  `n = 5`, matching the README's "3-5 replicates per promoter" target.
- `tests/test_backend_aware_offset.py` — 11 unit tests covering
  shrinkage behavior, synthetic recovery, JSON round-trip, and CLI
  smoke. (Shipped.)
- A Markdown report (`backend-offset-report.md`) generated by the CI
  workflow (`ci.yml` -> `backend-aware-offset` job) and uploaded as a
  workflow artifact on every push to `main`.

**Success criteria:**

1. The per-backend mean offset differs measurably from the global
   mean for **at least one** non-`ibm_fez` backend (sanity check that
   the estimator is doing real work).
2. With **≥ 5 backends × ≥ 5 replicates each** (a 25-job batch), the
   per-backend standard deviation of the offset is below `0.02` for
   each backend. Above that, the shrinkage prior is too weak to
   stabilize the per-backend estimate.
3. The shrinkage-augmented estimate reduces the cross-backend
   weighted-MSE versus the legacy single-offset estimate by **at
   least 30 %** on synthetic noise (verified by the existing
   `test_recovery_on_synthetic_three_backends` and an extension).

**Dependencies:** none beyond `quantum_calibration_report.json`
already in the repo.

**Risks:**

- *Single backend in current data:* the shipped report has only
  `ibm_fez`. The estimator handles this gracefully (degenerate case:
  shrunk offset equals mean offset), but the success criteria cannot
  be evaluated until a multi-backend batch exists.
- *Sample-size sensitivity:* with `n < 3` the per-backend std is
  unreliable. The shrinkage prior protects against this by design,
  but the operator must understand the resulting estimate is
  conservative, not aggressive.

**Out of scope for P0:**

- Within-promoter variance (P1).
- Between-promoter effect size (P1).
- Any algorithmic task (P2).

## P1 — Replicate-aware calibration

**Window:** Month 3–4.

**Deliverable:** an extension to `quantum_calibration_framework.py`
that, on top of the per-backend offset from P0, also reports:

- **Within-promoter mean / variance** for each (promoter, backend)
  cell with `n ≥ 3` replicates.
- **Between-promoter effect size** (Cohen's *d* or Hedges' *g*)
  comparing each promoter's offset to the global mean.
- **Calibration residual distribution** at the batch level (Q-Q plot
  data, skewness, kurtosis) so an operator can see whether the
  residual is approximately Gaussian — a prerequisite for the
  tolerance check `deviation ≤ 0.15` to mean anything statistical.

**Success criteria:**

1. For each promoter with `n ≥ 5` replicates on a single backend,
   the **95 % confidence interval** on the offset does not bracket
   zero. (This is the first time the offset is "real" in a frequentist
   sense.)
2. The residual distribution passes a Shapiro-Wilk normality test at
   `p > 0.05` for at least one promoter with `n ≥ 10` (relaxed:
   `p > 0.01` for `n ≥ 5`).

**Dependencies:** P0 (per-backend estimator), `qiskit-ibm-runtime`
for batch job submission, and a budget of `≥ 25` hardware jobs.

**Risks:**

- *Batch cost:* a 25-job calibration batch at the current 5-shot
  estimate is real money. The roadmap assumes a paid IBM Quantum
  plan; if only the Open plan is available, P1 may need to be
  reduced to 2 backends × 5 replicates.
- *Backend drift:* IBM recalibrates backends on a weekly schedule.
  If P1's batch spans a recalibration, the residuals become
  bimodal. Mitigation: timestamp every job and reject any batch
  that straddles a recalibration.

## P2 — Small variational agent benchmark

**Window:** Month 5–8.

**Deliverable:** a variational quantum eigensolver (VQE) agent that
solves a small but non-toy problem — a 4-qubit molecular Hamiltonian
with 2 variational parameters — under the calibrated noise model.
"Under the calibrated noise model" means:

- The agent simulates runs using the per-backend offset from P0
  rather than a generic depolarizing channel.
- The agent's reported ground-state energy is compared to the
  noise-free reference and to the uncalibrated-noise baseline.

**Success criteria:**

1. The calibrated-noise agent finds a ground-state energy within
   `0.05 Ha` of the reference on at least 3 of 5 random initial
   parameter settings.
2. The uncalibrated-noise agent fails the same test (i.e. the
   calibration is doing real work, not noise reduction for its own
   sake).

**Dependencies:** P0 + P1 (the offset and the residual distribution
are inputs to the noise model); `qiskit-nature` for the Hamiltonian;
`qiskit-algorithms` for VQE.

**Risks:**

- *Hardware availability:* `ibm_fez` and similar premium backends
  may not be available to the project at P2 time. Fallback:
  `qiskit_aer` with a synthetic noise model derived from the P1
  residuals.
- *Variational training time:* VQE on noisy hardware is slow. A
  4-qubit / 2-parameter problem should fit in `≤ 200` iterations
  on average; if it does not, the ansatz is the problem, not the
  noise model.

## P3 — Logical-qubit noise robustness

**Window:** Month 9–12.

**Deliverable:** rerun P2's benchmark on the cleanest available
quantum hardware. In priority order:

1. IBM's surface-code logical-qubit backend (if exposed via
   `qiskit-ibm-runtime` by P3 time).
2. `ibm_fez` with the `repcode_code[3]` repetition code wrapper.
3. `qiskit_aer` with the P1 residual distribution as the noise
   source.

**Success criteria:**

1. The P2 benchmark passes (criteria above) on at least one
   hardware target.
2. The calibrated-noise model from P0 / P1 transfers: the *a
   priori* prediction of ground-state energy matches the *a
   posteriori* measurement within the residual distribution's
   95 % interval.

**Dependencies:** P0–P2 all complete; hardware availability;
potentially an IBM research collaboration.

**Risks:**

- *Hardware lockout:* if the project cannot access the right
  backends by Month 12, P3 falls back to a fully simulated
  comparison. That is still publishable but is a smaller claim.

## What this roadmap explicitly does NOT promise

- *AGI.* This is a 12-month roadmap for one specific piece of
  evidence that quantum hardware can carry a calibrated inference
  workload. It is **not** a claim that quantum hardware is on a
  path to artificial general intelligence. The repo's name is
  historical; the scientific content is calibration + small
  variational experiments.
- *Quantum advantage.* None of the four phases attempts to show a
  quantum speedup over a classical baseline. That is a separate
  research program and would require its own roadmap.
- *Logical qubit correctness.* P3 measures robustness, not fault
  tolerance. Full fault-tolerant computation remains an open
  problem.
